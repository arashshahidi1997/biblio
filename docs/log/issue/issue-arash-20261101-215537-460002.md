# [from lit-studio, R52] add zotero --local: fall back to Zotero storage for imported_url PDF attachments too

## From

lit-studio, the personal field knowledge base and talk workspace (formerly journal-club), `~/dev/projects/lit-studio` (laptop main copy; gamma2 `/storage2/arash/projects/lit-studio`). How it works with other projects: `docs/for-other-projects.md`. Current run: graph-logos / knowledge-base principles (`backlogs/2026-10-30-graph-logos.md`), pixecog literature (J27).

## Problem

`biblio add zotero --local <key>` reports "pdf: failed — PDF could not be downloaded (web API: is the file synced to zotero.org?)" although the PDF is on disk in Zotero's storage. `fetch_pdf` (`src/biblio/zotero_add.py`, ~line 324) only falls back to `_from_storage` when `linkMode == "imported_file"`. PDFs saved by the Zotero Connector from a publisher page have `linkMode == "imported_url"`, so they are never looked up locally; the local API's `file()` does not return them either.

## Evidence

2026-11-01, laptop, biblio 0.3.4: `biblio add zotero --local DIZUL9NI UVSCSFN8 EFUJHTA5` (Nunez 1997, Chen 2006, Dhamala 2008; all ScienceDirect captures) → "3 no PDF". The attachments (SDE5X4SM, E7W4RYMV, 8JVZJ8JU) are `imported_url`, `application/pdf`, and the files exist in `~/snap/zotero-snap/common/Zotero/storage/<att>/`, which `zotero_storage_dirs()` already lists. Same with `ZOTERO_DATA_DIR` set. Copied by hand as a workaround (lit-studio commit ae065290).

## Request

In `fetch_pdf`, accept `imported_url` as well as `imported_file` for the storage fallback (both are stored copies; only `linked_file`/`linked_url` are not). A test with an `imported_url` child would cover it.

## How lit-studio will use it

Every paper the user captures through the Zotero Connector on the laptop enters this way (no bulk fetching; papers via Zotero only), so most new captures hit this.

lit-studio R52 in `backlogs/2026-10-23-alemanzapata-tooling.md` (requests table).

## Update 2026-11-02 (lit-studio): two more asks in the same command, from a day of real use

Over the 2026-11-02 run, 37 captures went through `biblio add zotero --local`; the `imported_url` gap hit about half of them (Connector captures from publisher pages), every batch. lit-studio worked around it in `code/ingest.py` (laptop copy), which also shows the two asks below working.

1. **Resolve by DOI.** `biblio add zotero --local --doi <doi> ...`: look the item up by DOI in the local library; when several items share the DOI (common: re-captures, merged libraries), take the one with a PDF on disk and say which. Today the user gives DOIs and the session has to find keys by reading a copy of zotero.sqlite.
2. **Check the PDF belongs to the entry before writing it.** On 2026-11-02 a hand-mapping put Chrobak & Buzsáki 1996's PDF under `buzsaki_2003_HippocampalNetwork`; nothing flagged it. A check that the title's opening words (first six, letters/digits only, hyphenation joined) appear on the PDF's first page separated eight papers cleanly (8×8 test: only the diagonal matched); a looser "most title words on pages 1–2" check did not (a short generic title matched a neighbour's PDF). Book chapters often fail it (title not on page 1), so a failure should warn, not block, when there is one candidate PDF.

lit-studio will move `code/ingest.py`'s steps into biblio once these exist, and keep only the gamma2 orchestration.
